The journey of one POST /schedule

How a single ship-scheduling request travels across two services — a Java orchestration layer and a Python model — and comes back with an ETA and a berth.

The two-hop map

The itinerary, step by step

OUTBOUND — from raw AIS state to a prediction
1

Client sends the request Client → Spring

A vessel's current AIS state plus its destination berth, as camelCase JSON.

POST http://localhost:8080/api/ships/schedule { "vesselId": "V001", "lat": 62.7375, "lon": 7.2000, "sog": 13.0, "cog": 220.0, "destLat": 61.6021, "destLon": 5.0555 }
2

Route, deserialize & validate Spring

PortController.schedule() receives the body. Jackson maps it to a ScheduleRequest record; @Valid checks @NotBlank vesselId, @PositiveOrZero sog, @Min(0)@Max(360) cog. A failure returns 400 here — nothing downstream runs.

3

Delegate to the ETA service Spring

The controller calls etaService.predict(req) first — the berth can't be assigned until the ETA is known.

⇆ camelCase → snake_case Data-shape translation #1: EtaRequest tags its fields @JsonProperty("dest_lat") so Jackson writes snake_case — the naming the Python service expects.
4

The cross-language HTTP call Spring → FastAPI

RestClient POSTs to the model service — forced to HTTP/1.1, because the JDK client's default HTTP/2 h2c upgrade is rejected by uvicorn and silently drops the body.

POST http://localhost:8000/predict (HTTP/1.1) { "lat": 62.7375, "lon": 7.2, "sog": 13.0, "cog": 220.0, "dest_lat": 61.6021, "dest_lon": 5.0555 }
5

FastAPI validates FastAPI

Pydantic parses the body into a ShipState and enforces sog ≥ 0, 0 ≤ cog ≤ 360. Invalid input returns 422 back to Spring.

6

Rebuild the training features FastAPI

build_features() derives the exact inputs the model trained on — haversine_nm() and bearing_deg() are imported from the training module so serving and training can never drift — plus the naive_eta_min physics prior.

# 7 features, in trained column order distance_to_dest_nm sog cog bearing_to_dest_deg lat lon naive_eta_min
7

Model inference FastAPI

Features become a one-row pandas DataFrame; _model.predict(X) runs the XGBoost regressor (loaded once at startup). Negative predictions are clamped to 0 — an ETA can't run backwards.

8

FastAPI responds FastAPI → Spring

Returns the prediction as JSON, 200 OK.

{ "eta_minutes": 414.0, "eta_hours": 6.9, "distance_to_dest_nm": 21.4, "bearing_to_dest_deg": 214.8, "naive_eta_min": 98.8 }
⇆ snake_case → camelCase Data-shape translation #2: EtaResponse maps eta_minutes → etaMinutes. It declares only 3 fields; Jackson silently ignores the extras FastAPI sent.
RETURN — from a prediction to a berth assignment
9

Parse the ETA Spring

EtaService hands a typed EtaResponse back to the controller. Java is once again working in camelCase.

10

Business logic — assign a berth Spring

Now the ETA exists, berthService.assign(vesselId) runs. It's synchronized (thread-safe): first free berth → BERTHED B1; if all 4 are full → QUEUED with a number from an AtomicInteger.

11

Assemble the answer Spring

The controller combines the ETA (from FastAPI) and the berth (local logic) into one ScheduleResponse.

12

Response to the client Spring → Client

Serialized to JSON, 200 OK. Round trip complete.

{ "vesselId": "V001", "etaMinutes": 414.0, "etaHours": 6.9, "status": "BERTHED", "berthId": "B1", "berthName": "Berth 1", "queueNumber": null }

One request, three representations

Spring Boot Orchestration, validation, berth & queue business logic camelCase the wire The contract between a Java service and a Python one snake_case JSON FastAPI Stateless feature-building + model inference only snake_case → pandas

Spring never learns how the model works; FastAPI never learns that berths exist. The @JsonProperty annotations are the adapters that let two naming conventions talk without either side compromising — exactly how a model gets deployed as a stateless microservice behind an application that owns the domain.
